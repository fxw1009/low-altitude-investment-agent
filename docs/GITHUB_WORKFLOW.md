# GitHub 协作工作流

> [!IMPORTANT]
> 本仓库面向“成员主要通过指挥 Codex 产出代码”的协作方式设计。**GitHub 是唯一任务源、成果审阅点和进度看板。**

## 任务从 Issue 开始

每个开发任务都必须有一个 Issue，使用模板写明：**目标、输入输出、验收标准、相关数据与风险**。成员领取后，**不得在 `main` 直接提交**。

```text
Issue → Codex 在任务分支实现 → Pull Request → 自动检查 → 评审/合并 → Issue 自动关闭
```

## 成员给 Codex 的标准指令

```text
请处理 GitHub Issue #编号。
在分支 feat/对应模块-简短名称 中实现，不修改无关文件。
完成后运行相关检查，提交清晰的 commit，并创建 Pull Request。
PR 描述必须写明：Closes #编号、实现内容、验证方式、数据来源与未解决风险。
```

## 分支

- `main`：仅存放已验收、可运行版本；
- `feat/knowledge-graph-*`：产业链与图谱；
- `feat/wind-scoring-*`：Wind 数据和量化；
- `feat/event-evidence-*`：政策、事件与证据；
- `feat/frontend-*`：前端和可视化；
- `feat/orchestrator-*`：总控 Agent 和接口整合；
- `fix/*`、`docs/*`：修复与文档。

## Pull Request 最低标准

1. **一个 PR 对应一个可验证目标**，避免混合无关改动；
2. **描述关联 Issue，说明测试结果和数据来源；**
3. **不提交 Wind 原始导出、账号、密钥或受限研报全文；**
4. 修改接口时同步更新 `contracts/` 和 README；
5. 合并前至少由队长检查一次，涉及图谱/财务口径时由相应负责人复核。

## 看板状态

- `待领取`：任务已定义；
- `进行中`：成员已领取且有分支/PR；
- `待审查`：PR 已创建；
- `已完成`：PR 合并且 Issue 自动关闭；
- `阻塞`：缺数据、口径不明或需要队长决定。

## 每日异步更新

成员在 Issue 评论中用以下格式更新即可，不需要额外会议：

```markdown
### 今日更新
- 已完成：
- 正在做：
- 阻塞项：
- 下一步：
```
